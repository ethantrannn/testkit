# Spec patterns (Playwright Test, TypeScript)

How a testkit case becomes a Playwright test. Every example below ran green against a local test app with `@playwright/test` 1.65.1.

## File skeleton

`qa/automation/tests/<RUN_ID>/<STREAM_ID>-<feature-slug>.spec.ts`, one file per stream (or per feature when several streams of a ticket test the same screen):

```ts
// testkit-run: PROJ-123
// Source: qa/runs/PROJ-123/cases/S1.md + results/S1.md. Generated by testkit-automate; keep titles starting with the TC id.
import { test, expect } from '@playwright/test';
import { authFile, credentials, SIGNED_OUT } from '../support/accounts';
import { unique } from '../support/data';

test.describe('PROJ-123 S1 — Sign in', () => {
  // tests
});
```

The `// testkit-run:` line tells `coverage.py` which run's TC ids the file uses (TC ids repeat across runs). Keep it in the first 5 lines.

## Case → test mapping

```ts
test('TC-S1-001 Sign in with a valid email and password', { tag: '@smoke' }, async ({ page }) => {
  const member = credentials('member');
  await test.step('1. Open /login', async () => {
    await page.goto('/login');
  });
  await test.step('2-3. Fill Email and Password', async () => {
    await page.getByLabel('Email').fill(member.email);
    await page.getByLabel('Password').fill(member.password);
  });
  await test.step('4. Click "Sign in"', async () => {
    await page.getByRole('button', { name: 'Sign in' }).click();
  });
  // one assertion per Expected bullet
  await expect(page).toHaveURL(/\/dashboard$/, { timeout: 3_000 });   // "within 3 s"
  await expect(page.getByRole('heading', { name: 'Your notes' })).toBeVisible();
});
```

| Case field | In the test |
|---|---|
| `### TC-S1-001 — <title>` | test title `TC-S1-001 <title>` (exact TC id first, then the case title) |
| `Priority: P0` | `{ tag: '@smoke' }` (P1/P2: no tag; add `@p1` only if the team wants a P1 suite) |
| `Preconditions` | `test.use({ storageState })`, `beforeEach`, or data created through the UI/API at the start of the test |
| `Test data` placeholders | `credentials('<role>')` for `{{role.*}}`; `unique('<label>', testInfo)` for data the case creates |
| `Steps` | `test.step('<N>. <step>', ...)` when the case has 4+ steps (the trace and HTML report then show the case's own steps); plain lines otherwise |
| each `Expected` bullet | at least one web-first `expect` (`toHaveURL`, `toHaveText`, `toBeVisible`, `toHaveValue`, `toHaveCount`, `toBeDisabled` …) checking exactly what the bullet says |
| "within N s" | the `timeout` option of that assertion |
| "No console errors" | `page.on('console')` / `page.on('pageerror')` collected into an array, `expect(errors).toEqual([])` at the end |
| an HTTP status | `const resp = page.waitForResponse(r => r.url().includes('/api/profile') && r.request().method() === 'PATCH')`, then after the click `expect((await resp).status()).toBe(200)` |

An expected bullet that cannot be checked by code (visual judgement, "looks aligned", an email in a real inbox with no API) is never dropped silently. If the other bullets still make a meaningful test, automate them and leave a comment in the test: `// not automated: <bullet> (<reason>)`. If nothing meaningful is left, the case is `manual-only` with that reason.

## Locators

Priority order, use the first that is unique and stable:

1. `page.getByRole('button', { name: 'Sign in' })` — role + accessible name (what the case's step names in quotes).
2. `page.getByLabel('Email')` — form fields by their label.
3. `page.getByTestId('account-name')` — `data-testid` (configure another attribute with `use: { testIdAttribute: 'data-qa' }` in the config).
4. `page.getByText('Saved', { exact: true })`, `getByPlaceholder`, `getByAltText`, `getByTitle`.
5. CSS only as a last resort and scoped (`page.locator('form#login').getByRole(...)`), never XPath, never `nth()` on a long list without a filter, never generated class names (`.css-1x2y3z`).

Narrow with `filter` and chaining: `page.getByRole('row').filter({ hasText: orderId }).getByRole('button', { name: 'Cancel' })`.

If no stable locator exists, write it with the best available one and list it under "Testability requests" in your summary (e.g. "add `data-testid` to the account menu").

## Known bugs (`test.fail`)

A case that FAILED in the manual run and has a bug (status `open` or `reopened`) is automated with the **correct expectation from the case**, marked as expected to fail:

```ts
test.fail(
  'TC-S1-003 Dashboard header shows the display name',
  { annotation: { type: 'bug', description: 'BUG-PROJ-123-S1-01 header shows the email instead of the name' } },
  async ({ page }) => {
    const { name } = credentials('member');
    test.skip(!name, 'Set TESTKIT_E2E_MEMBER_NAME');   // a missing env var must not look like the known failure
    await page.goto('/dashboard');
    await expect(page.getByTestId('account-name')).toHaveText(name!);
  },
);
```

- While the bug is open the test fails as expected and the run is green.
- When the developer fixes it, Playwright reports `Expected to fail, but passed.` and the run goes red: that is the signal to verify the bug (`testkit-verify`) and then turn `test.fail(` into `test(`.
- Inside a `test.fail` test, any failure counts as expected, so check setup problems with `test.skip(cond, reason)` before the real assertion.
- Bugs with status `wont_fix`: write the test to the *accepted* behaviour only if product confirmed it in the bug file; otherwise leave the case `manual-only` with the reason.
- Never use `test.fixme`/`test.skip` to hide a failure you do not understand.

## Signed-in and signed-out tests

`tests/auth.setup.ts` signs in once per role (setup project) and saves `.auth/<role>.json`. Specs pick a role:

```ts
test.describe('signed in as member', () => {
  test.use({ storageState: authFile('member') });
  // ...
});
test.describe('signed out', () => {
  test.use({ storageState: SIGNED_OUT });
  // login, signup, password reset cases
});
```

Edit `ROLES` and the sign-in steps in `auth.setup.ts` to match the product (same locators as the sign-in case). Tests that log out, change the password or delete the account must use their own freshly created account (see Test data), never the shared role account, or every later test loses its session.

## Test data

- Anything a test creates gets a name from `unique('<label>', testInfo)` (`e2e-<run tag>-<project>-w<worker>-<label>`). `TESTKIT_RUN_TAG` is shared by all workers of one run; set it in CI (`TESTKIT_RUN_TAG=e2e-${{ github.run_id }}`) if you want to find the data afterwards.
- Assert on your own record (`getByText(text, { exact: true })`, a row filtered by the unique name), never on list counts or "the first row", because other runs share the environment.
- New accounts for a test: `uniqueEmail('member', testInfo)` and the same account strategy the executor uses (`accounts.strategy` in `qa/config.yml`: signup UI, API call with the token from the env var, or the seed command).
- Clean up through the API or `accounts.cleanup` in an `afterAll` when the product allows it; otherwise rely on the unique prefix.
- Never depend on data made by another test file. Tests run in parallel and in any order (`fullyParallel: true`).

## Page objects

Only when **3 or more spec files** use the same screen. Put them in `tests/pages/<screen>.ts`: locators as readonly fields, actions as methods, **no assertions inside** (assertions stay in the test so it reads like the case).

```ts
import type { Page, Locator } from '@playwright/test';
export class LoginPage {
  readonly email: Locator; readonly password: Locator; readonly submit: Locator;
  constructor(readonly page: Page) {
    this.email = page.getByLabel('Email');
    this.password = page.getByLabel('Password');
    this.submit = page.getByRole('button', { name: 'Sign in' });
  }
  async goto() { await this.page.goto('/login'); }
  async signIn(email: string, password: string) {
    await this.email.fill(email); await this.password.fill(password); await this.submit.click();
  }
}
```

## Things that make suites flaky

- `page.waitForTimeout(...)` — forbidden; wait for a state with a web-first assertion instead.
- `expect(await locator.textContent()).toBe(...)` — no retry; use `await expect(locator).toHaveText(...)`.
- `page.waitForLoadState('networkidle')` on apps with polling or websockets.
- Shared accounts mutated by tests; assertions on counts in shared lists; time-of-day dependent data.
- Animations: assert the final state (`toBeVisible`, `toHaveCSS`), do not sleep.

## Reading a failure

Each failed test leaves in `qa/automation/test-results/<test>-<project>/`:

- `error-context.md` — the error, the call log (what the locator resolved to, the received value), and an ARIA snapshot of the page. Read this first.
- `test-failed-1.png` — screenshot at the failure. Open it and look at it.
- `trace.zip` — full trace (DOM snapshots, network, console, each action). `npx playwright show-trace <path>` opens the viewer; to inspect without a GUI, unzip it: `test.trace` and `*-trace.trace` are JSON lines, `*.network` holds the HTTP log.

Traces and reports contain every value typed by the test, **including passwords** of the test accounts. Keep them out of git (the suite's ignore file does), give CI artifacts a short retention, and never attach them to public issues.
