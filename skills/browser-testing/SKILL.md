# Browser testing conventions

`qa/config.yml` → `browser.tool` picks the tool:

| `browser.tool` | Use |
|---|---|
| `browser-use` (default) | The Browser Use CLI, wrapped by `scripts/bu-session.sh` in this skill folder. Full command reference: the `browser-use` skill next to this one (generated by `testkit init` for the installed version). |
| `agent-browser` | The agent-browser CLI. Reference: `references/agent-browser-core.md`. See section 6. |
| `playwright-mcp`, `chrome-devtools-mcp` | The MCP tools of that name, with the same session, evidence and safety rules. |

## 1. One isolated session per stream

Several executors run in parallel, so each stream has its own session and never touches another stream's browser. Name it `<RUN_ID>-<STREAM_ID>` (writer exploring: `...-explore`; reviewer: `...-review`; verify: `verify-<BUG_ID>`).

```bash
SK=$(ls -d .claude/skills .agents/skills 2>/dev/null | head -1)   # the skills folder testkit installed into
BU=$SK/browser-testing/scripts/bu-session.sh

$BU run PROJ-123-S2 <<'PY'
new_tab("https://staging.example.com/login")
wait_for_load()
print(page_info())
PY

$BU stop PROJ-123-S2     # always stop your session when the stream ends
```

`run` starts the session on first use and reuses it after that, so the page, cookies and login survive between calls. `new_tab(url)` only for the first navigation of a session; after that use `goto_url(url)` and `wait_for_load()`.

`browser.mode` in `qa/config.yml` decides what a session is:

| mode | What runs | Parallel | Cost |
|---|---|---|---|
| `isolated` (default) | A separate headless Chrome per session with a temporary profile | yes | free |
| `cloud` | A Browser Use Cloud browser per session (needs `browser-use login`) | yes | billed per hour; ask the user before the first cloud session of a run, and stop every session you start |
| `local` | The user's running Chrome, with their logins | **no**, one session at a time | free |

`cloud` cannot reach `localhost`. For a local dev server, ask the user for a tunnel URL (or permission to start `cloudflared tunnel --url http://localhost:PORT`) and test the public URL.

## 2. Driving the page (browser-use)

Each `run` is a Python snippet; browser-use helpers and the testkit helpers below are pre-imported.

- **Find elements with the accessibility tree**, not by guessing coordinates: `cdp("Accessibility.getFullAXTree")["nodes"]` gives role, name and `backendDOMNodeId`; filter in Python before printing. Box centre: `q = cdp("DOM.getBoxModel", backendNodeId=n)["model"]["content"]; x, y = sum(q[0::2])/4, sum(q[1::2])/4`, then `click_at_xy(x, y)`.
- **Inputs**: `fill_input("input[name=email]", "qa+s2@example.test")`, or click then `type_text(...)`; `press_key("Enter")`; `upload_file(selector, path)`.
- **Waiting**: `wait_for_load()` after navigation, `wait_for_element(selector, timeout=10)`, `wait_for_network_idle()`. Use `wait(seconds)` only for animations.
- **Reading state**: `page_info()` (url, title, size), `js("document.querySelector('.toast').textContent")`.
- **Mobile layout**: `cdp("Emulation.setDeviceMetricsOverride", width=375, height=812, deviceScaleFactor=3, mobile=True)`; reset with `cdp("Emulation.clearDeviceMetricsOverride")`.
- **Failure simulation**: `cdp("Network.emulateNetworkConditions", offline=True, latency=0, downloadThroughput=-1, uploadThroughput=-1)` for offline.
- Stuck on a mechanic (iframes, shadow DOM, dialogs, downloads, drag and drop)? Read the `browser-use` skill's interaction section before improvising.

## 3. Evidence

Evidence folder: `qa/runs/<RUN_ID>/evidence/<STREAM_ID>/`. testkit helpers (from `scripts/agent_helpers.py`):

| Helper | Does |
|---|---|
| `tk_clear()` | Forget console/network events seen so far. Call at the start of every case. |
| `tk_evidence(base, full=False)` | Saves `<base>.png`; if console errors, JS exceptions, HTTP ≥ 400 or failed requests happened since the last call, also `<base>.json`. Returns a summary with the problem count. |
| `tk_problems()` | The same problem list, without a screenshot. |

| When | Call | Base name |
|---|---|---|
| Writer explores a screen | `tk_evidence(".../explore-<screen>")` | `explore-<screen>` |
| Executor checks an expected result | `tk_evidence(".../<TC_ID>-step<N>")` | `<TC_ID>-step<N>` |
| A case fails | `tk_evidence(".../<TC_ID>-fail", full=True)` | `<TC_ID>-fail` |
| A bug is hard to describe in steps | `start_recording("<TC_ID>", title=...)` … `stop_recording()`; keep the returned folder path in the result | — |

```bash
$BU run PROJ-123-S2 <<'PY'
tk_clear()
fill_input("input[name=displayName]", "a" * 256)
# ... click Save via the AX tree ...
wait_for_network_idle()
print(tk_evidence("qa/runs/PROJ-123/evidence/S2/TC-S2-004-step4"))
PY
```

Open every screenshot you rely on (view the image file) and look at it, and read the `.json` when the summary reports problems. A screenshot you did not look at is not evidence. A page that looks fine but logged errors is not a clean pass: note the problems in the result.

## 4. Safety

- Only open base URLs of environments listed in `qa/config.yml`. If a case needs another host, stop and report it.
- Never run destructive actions (delete, bulk update, payments, emails to real users) on an environment whose config says `allow_write: false`. Mark those cases `BLOCKED` with the reason.
- Type only the test accounts from `qa/accounts.local.json`. In `local` mode the browser holds the user's real logins: do not change account settings, send messages or buy anything with them, and stop at password, MFA or consent screens.
- Never paste secrets into result files, bug reports or `browser-use feedback`. Write `{{member.password}}` instead.
- browser-use telemetry is off in testkit sessions (`ANONYMIZED_TELEMETRY=false`) so internal URLs are not sent anywhere; leave it off unless `browser.telemetry: true`.
- Stop what you start: `$BU stop <name>` at the end of every stream, `$BU stop-all` if a run is aborted. Cloud sessions keep billing until stopped.

## 5. Cross-browser and devices

Manual sessions run Chrome. Cover other engines and devices like this, and say in the result which ones were covered:

| Need | How |
|---|---|
| Phone/tablet layout in Chrome | `Emulation.setDeviceMetricsOverride` (section 2), with `qa/config.yml` `browser.mobile_viewport`; also set a mobile user agent with `cdp("Emulation.setUserAgentOverride", userAgent=...)` when the site serves different markup |
| Firefox and Safari (WebKit) engines | Run the automated regression suite with its `firefox`/`webkit` projects (`testkit-automate` skill) for the ticket's specs |
| Real devices, many OS/browser versions | `browser.mode: cloud`, or a device cloud the team already pays for; ask the user first |
| Native or hybrid app | `mobile-testing` skill |

## 6. Troubleshooting

- `bu-session: Chrome/Chromium not found` → install Chrome, or set `browser.chrome_path` in `qa/config.yml`.
- A call hangs or the session is dead → `$BU status`, then `$BU stop <name>` and run again (a fresh session loses the login; redo the preconditions).
- `browser-use --doctor` checks the CLI install; `testkit doctor` checks everything testkit needs.

## 7. agent-browser (when `browser.tool: agent-browser`)

Same rules; commands differ. Every command carries the session: `agent-browser --session "<RUN_ID>-<STREAM_ID>" open <url>`, `snapshot -i` for `@refs` (take a new snapshot after every DOM change), `fill`, `click`, `wait --text`, `screenshot [--full] <path>`, `console` and `errors` (clear with `--clear` at the start of a case), `network requests`, `set viewport 375 812`, `network route <pattern> --abort`, `record start|stop`, `close` at the end. Full reference: `references/agent-browser-core.md` when present, else `agent-browser skills get core --full`.
